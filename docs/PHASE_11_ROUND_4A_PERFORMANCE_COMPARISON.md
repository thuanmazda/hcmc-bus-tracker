### Key Takeaways from Simulation
1. At **20 routes**, Sequential (`C=1`) takes `~26.7s`, exceeding the `15s` polling interval (impossible to maintain 15s cadence without overlapping).
2. **Bounded (`C=4`) / Adaptive (`C=1..4`)** finishes 10 routes in `~3.3–3.6s` and 20 routes in `~6.8–7.0s` without saturating Cloudflare concurrency limits.
3. Going above `C=5` (`C=10`) yields diminishing cycle speedup (`6.8s -> 5.6s`) while exploding per-request queuing latency and simulated `429` rejections (`0 -> 17`), proving `C <= 4` global cap (paired with shared-stop coalescing!) is the sweet spot.

## 2. Comprehensive Evaluation of Latency Reduction Solutions (Section 5)

| Proposed Solution | Reduces HTTP / Acquisition Latency? | Makes Underlying GPS Timestamp (`dts`) Fresher? | Feasibility Status |
| :--- | :--- | :--- | :--- |
| **Bounded Concurrent Polling (`C <= 4`)** | **Yes** — cuts multi-checkpoint / multi-route sweep time from ~`13–27s` down to `~1.7–7.0s` | **No** — server still emits Tier-1 (`34–50s`) & Tier-3 (`171–205s`) `dts` ticks | **High** (partially implemented per-route; can globalize safely) |
| **Adaptive Concurrent Polling + Shared-Stop Coalescing** | **Yes** — eliminates duplicate hub requests & gracefully avoids `429` cooldown stalls | **No** — cannot accelerate upstream GSHT/EBMS ingestion | **High** (recommended Round 4B transport upgrade) |
| **Dedicated Direct GPS Endpoint** | Would cut checkpoint sweep overhead if 1 call returned `(lat, lng)` per route | **Only if** fed from a lower-latency upstream gateway | **Unfeasible on public API** — verified `UNAVAILABLE` across all EBMS & `buyttphcm.com.vn` bundles |
| **Fleet-Wide Live Endpoint** | Would replace multi-stop sampling with 1 call | Depends entirely on upstream freshness | **Unfeasible on public API** — verified `UNAVAILABLE` (not exposed publicly) |
| **WebSocket / SSE Push** | Would eliminate 0–15s polling phase lag (`~7.5s` avg saving) | Would deliver server tick immediately upon compute, still bounded by EBMS origin `34–186s` | **Unfeasible on EBMS** — backend & CDN offer REST HTTP GET only (`UNAVAILABLE`) |
| **Client-Side Prediction Caching & Shared Stop Deduplication** | **Yes** — reuses fresh `< 10s` responses when switching tabs/routes without extra network wait | **No** — cached snapshot preserves original `dts` | **High** (safe optimization) |

## 3. Direct Honest Answers to Section 5 Questions

1. **Can GPS age be reduced from `120–188s` to `< 60s` via app-side changes alone?**  
   - **NO (for Tier-3 routes like `01`, `31`, `44`, `65`, `86`, `102`, `152`).** Even immediately after EBMS publishes a brand-new `dts` tick, `age_srv = Date - dts` on those routes is already **`171–188s`**. Meanwhile, Tier-1 routes (`33, 38, 60-1, 69, DL02`) *naturally* sit at **`34–50s`** on the exact same API! Polling faster only reduces client *waiting lag between ticks* (`0–15s` -> `0–10s`), NOT the server-published `171–188s` `dts` age.
2. **Can GPS age be reduced to `10–30s`?**  
   - **NO.** Not even the freshest Tier-1 routes (`69`: `34s` min) achieved `< 30s` in our 56-sample multi-stop sweep, and public EBMS does not expose a push stream or sub-30s raw blackbox feed.
3. **What conditions are required to achieve `< 30s` real-time GPS age?**  
   - Authorized partnership / B2B integration with Sở GTVT / Trung tâm QLGTCC TP.HCM or fleet GSHT telemetry providers granting access to an authenticated raw-GPS / GTFS-RT VehiclePositions stream (bypassing multi-minute batch aggregation), plus server-side WebSocket/SSE or push-relay infrastructure.
4. **What limits are strictly outside the Android app's control?**  
   - On-board GSHT modem transmission cadence (`10–30s`), bus operator vendor gateway batching delays (`~35s` floor on Tier 1 up to `+140s` on Tier 3), EBMS backend map-matching/prediction cadence, and Cloudflare WAF request-rate caps.
5. **What is the best possible solution if EBMS continues supplying aged data?**  
   - Combine **(a) Bounded Adaptive Polling + Shared-Stop Coalescing** (so newly published EBMS ticks reach the UI rapidly without HTTP `429` risk or redundant stop calls) with **(b) Transparent Bounded Delay Compensation & Polyline Interpolation** already implemented in `PositionCompensationEngine` (Round 2: continuous physical `0..120s` + attenuated `120..190s` tail projection + freeze guard on stagnant ticks + honest UI source/latency labeling from Round 3).
